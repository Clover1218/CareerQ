# CareerQ 三人全栈模块开发计划

> 状态：三人讨论稿，模块负责人及共同约定需在开工会确认
> 适用项目：CareerQ（职问桥）响应式 Web 站点
> 开发方式：三名成员分别负责一个业务模块的前端、后端、数据访问、测试和联调；不按前端/后端拆人

## 1. 文档目的

本文把“三个人按模块开发，每个人都负责全栈”的想法整理成可执行的分工建议。三人确认后，可据此拆 Issue、建立分支和 PR，并在模块验收时按统一标准集成。

当前仓库已有 Vue 3 + TypeScript + Vite 前端，以及 Java 21、Spring Boot 3、MyBatis、Flyway、MySQL 8（本地开发使用 H2）的后端。本文按现有技术栈和已有 API 设计，不要求为分工调整框架。

本文中的王、季、李是建议负责人，最终负责人由三人讨论确定。负责人对模块端到端结果负责，但不独占代码；其他成员可以通过 Issue 和 PR 协助。

## 2. 分工原则

1. 每个业务模块有一名主负责人，覆盖页面与交互、接口与业务逻辑、数据访问、测试和联调。
2. 模块按用户能完成的一段业务流程划分，尽量减少跨模块改同一页面、接口或数据库表。
3. 登录会话、角色、统一响应、CSRF、状态枚举和数据库迁移属于公共约定。先由三人共同定边界，再指定一名维护者；需要改动时提前通知受影响模块。
4. 模块负责人负责拆分任务、控制范围、提交 PR 和修复反馈；至少由另一名成员审查后再合并。
5. 不把“全栈负责”理解为单人独立决定公共接口。跨模块契约、数据模型和权限变化必须先同步。
6. 本文是建议方案。团队确认后，将负责人、排期和最终决策补入本文，避免口头结论与项目文档不一致。

## 3. 模块建议

| 模块 | 建议负责人 | 业务目标 | 主要用户 |
|---|---|---|---|
| A. 公开广场与内容浏览 | 王 | 游客能浏览公开问题及回答，登录用户能使用公开内容相关功能 | 游客、学生、HR |
| B. 账号与学生提问 | 季 | 学生能登录、提出问题并追踪自己问题的处理状态 | 学生 |
| C. HR 回答与运营审核 | 李 | HR 能回答问题并处理私密工单；运营能审核内容和举报 | HR、运营 |

### 模块 A：公开广场与内容浏览（建议：王）

**交付范围**

- 游客可访问首页、公开问题列表、问题详情和已发布回答。
- 支持按标签或现有契约提供的条件筛选；搜索能力按三人确认的 MVP 范围实现，不在首期擅自引入搜索服务。
- 展示公开内容状态、回答数量、时间、标签和必要的空态/错误态/加载态。
- 浏览已审核发布的公开沉淀内容及精选内容（若纳入 MVP）。
- 与学生/HR 模块约定公开问题和回答的展示数据结构；不直接复制另一模块的 DTO 或数据库实体。

**涉及接口（以当前实现和 OpenAPI 为准）**

- `GET /api/v1/questions`
- `GET /api/v1/questions/{id}`
- `GET /api/v1/posts`
- `GET /api/v1/feed/highlights`（是否纳入首期由三人确认）

**建议目录**

- 前端：`frontend/src/views/` 下公开列表、详情、公开内容页；相关公共展示组件由本模块维护。
- 后端：现有 Question、PublicPost API 与 Service 边界；若需增加公开查询能力，先更新接口契约。

**验收要点**

- 未登录用户可浏览已发布的公开内容。
- 未审核、已拒绝、已下架或私密内容不能通过公开接口泄露。
- 列表分页、无结果、接口失败、详情不存在等状态可正常使用。
- 桌面和窄屏视口下，问题标题、标签、回答正文和操作入口不重叠。

### 模块 B：账号与学生提问（建议：季）

**交付范围**

- 注册、登录、退出和当前用户状态；登录成功后按角色进入相应页面。
- 学生工作区、提问表单、公开/私密范围选择、我的问题列表及问题状态展示。
- 学生可查看自己有权查看的问题及其已通过审核的回答/追问。
- 提交表单校验、重复提交保护、错误提示、会话失效处理。
- 与 HR 模块协商私密问题建立、关闭和公开申请的状态交接，不在前端自行推断后端状态。

**涉及接口（以当前实现和 OpenAPI 为准）**

- `GET /api/v1/auth/csrf`
- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/logout`
- `GET /api/v1/me`
- `POST /api/v1/questions`
- `GET /api/v1/questions/mine`
- `POST /api/v1/questions/{id}/close`
- `POST /api/v1/questions/{id}/publish`

**建议目录**

- 前端：登录/注册、学生工作区和提问相关 View 与表单组件。
- 后端：现有 Auth、Question API/Service 能力；新字段或状态变更需通过契约评审和 Flyway 迁移。

**验收要点**

- 游客尝试写操作时会被引导登录，服务端仍实际拒绝未认证请求。
- 学生可提交公开或私密问题，并看到后端返回的真实状态。
- 学生只能查看自己的私密问题；其他学生不能通过修改 URL 或请求参数访问。
- 关闭和申请公开仅在服务端允许的状态下可用；刷新页面后状态仍与服务端一致。

### 模块 C：HR 回答与运营审核（建议：李）

**交付范围**

- HR 工作区、公开待回答问题池、私密待认领池和私密问题认领。
- HR 提交公开回答或私密回答，查看审核状态，并在获准范围内参与追问。
- 运营审核队列、内容详情上下文、通过/拒绝/下架操作和举报处理。
- 明确区分 HR 与运营的页面入口和权限；菜单隐藏不能代替服务端鉴权。
- 与公开广场模块约定已审核回答、公开沉淀及下架内容的可见性。

**涉及接口（以当前实现和 OpenAPI 为准）**

- `GET /api/v1/hr/question-pool`
- `GET /api/v1/hr/private-pool`
- `POST /api/v1/hr/questions/{id}/claim`
- `POST /api/v1/questions/{id}/answers`
- `GET/POST /api/v1/questions/{id}/followups`
- `GET /api/v1/admin/moderation/queue`
- `POST /api/v1/admin/moderation/{targetType}/{id}/decide`
- `GET /api/v1/admin/reports`
- `POST /api/v1/admin/reports/{id}/handle`

**建议目录**

- 前端：HR 工作区、回答/追问组件、运营审核和举报处理页面。
- 后端：现有 Hr、Answer、Followup、Admin、Moderation、Report API/Service 能力；跨域状态修改先更新契约。

**验收要点**

- HR 与运营页面按角色隔离，未授权角色的 API 请求返回无权限。
- HR 只能认领和回答符合规则的问题；私密问题身份信息按产品约定脱敏。
- 待审核的回答和追问只对允许的提交者/运营可见，不提前展示给对方或游客。
- 审核操作有明确结果反馈，刷新后队列和内容状态正确更新。
- 举报处理记录目标、处理结果和必要的备注；运营不应依赖浏览器本地状态作为最终记录。

## 4. 三人共同承担的边界

以下工作需要三人共同确认契约，但应指定一名具体维护者，避免“共同负责”变成无人维护。

| 共同约定 | 开工前要确定 | 维护建议 |
|---|---|---|
| 页面与路由 | 公共入口、学生入口、HR 入口、运营入口及登录后的落点 | 路由所在模块的负责人 |
| API 契约 | 字段、状态、分页、错误码、角色可见范围 | 对应 API 模块负责人；同步更新 `docs/接口契约-职问桥.md` 和 OpenAPI |
| 鉴权与权限 | 游客、学生、HR、运营、管理员的权限矩阵 | 后端安全配置维护者；所有业务负责人补充权限测试 |
| 数据库 | 表归属、字段变更、索引、迁移顺序和回滚策略 | 发起变更的模块负责人编写迁移，另一名成员审查 |
| 公共前端组件 | 导航、登录态、错误提示、状态标签和表单规范 | 指定一名 UI/组件维护者，避免多模块重复实现 |
| 测试与集成 | 单模块验收、跨模块场景和演示数据 | 每个模块自测；三人共同完成端到端验收 |

### 建议的权限矩阵

| 能力 | 游客 | 学生 | HR | 运营/管理员 |
|---|---:|---:|---:|---:|
| 浏览已发布公开内容 | 是 | 是 | 是 | 是 |
| 创建问题 | 否 | 是 | 按最终产品决策 | 按最终产品决策 |
| 查看自己的私密问题 | 否 | 是 | 否 | 按审核职责允许并留痕 |
| 查看 HR 待回答问题池 | 否 | 否 | 是 | 按管理职责允许 |
| 认领和回答 | 否 | 否 | 是 | 否，除非产品另行规定 |
| 审核内容与处理举报 | 否 | 否 | 否 | 是 |

以上矩阵是讨论起点；特别是 HR 是否可创建问题、运营是否能查看私密内容，应在开工前明确。

## 5. 本期范围与暂缓项

### 本期优先完成

- 游客公开浏览。
- 学生注册/登录、提问、查看自己的问题。
- HR 公开问题池、回答，以及私密问题认领和回答的演示闭环。
- 运营审核和基本举报处理。
- 基于现有 Cookie 会话与 CSRF 方案完成前后端联调。

### 明确暂缓

- 真实短信验证码供应商接入和短信发送限流。开发/演示环境按现有固定验证码方案工作；生产安全要求仍按当前后端配置执行。
- HR 真实身份材料审核、企业邮箱校验或第三方认证。演示阶段如需 HR 账号，使用团队准备的测试账号/种子数据，并明确这不代表完成真实认证。
- 未经团队确认的私信、实时聊天、站内通知、复杂搜索、复杂推荐和多组织权限。

暂缓不等于忽略接口安全：后端必须继续执行角色授权、私密数据访问控制、CSRF 和输入校验。

## 6. 开发顺序与交付节奏

### 阶段 0：共同定基线

- 确认每个模块唯一负责人和备份审查人。
- 确认权限矩阵、问题/回答/追问/审核状态、字段命名和统一响应格式。
- 确认页面路由与登录后跳转规则。
- 确认演示账号、固定验证码、种子数据和启动方式。
- 更新接口契约及 OpenAPI；把需要新增/变更的 API 和数据库迁移列成 Issue。

**完成条件：** 三人对模块边界、公共契约和第一批验收场景达成一致，关键决策写入本文或接口契约。

### 阶段 1：模块独立开发

- 各负责人从最新 `main` 创建独立分支，只开发自己模块及已协调的公共变更。
- 前端可先使用契约 Mock；后端接口通过单元/集成测试验证。
- PR 描述列明接口/表变更、权限变化、测试命令和截图或演示步骤。
- 至少另一名成员审查后合并；有冲突时由模块负责人协调，不直接覆盖他人提交。

### 阶段 2：端到端集成

- 按“游客浏览 → 学生提问 → 运营审核 → HR 回答 → 学生查看”的公开闭环验收。
- 按“学生私密提问 → HR 认领/回答/追问 → 学生结单 → 运营审核脱敏公开 → 游客浏览”的私密闭环验收。
- 验证越权、CSRF、无效状态提交、空数据和失败重试等边界。
- 修复集成问题后冻结演示版本，更新启动和演示说明。

## 7. 分支、PR 与代码审查约定

- 分支从最新 `main` 创建，命名示例：`feature/student-question-workspace`、`feature/hr-answer-flow`、`feature/public-browse`、`docs/three-fullstack-module-plan`。
- 每个 PR 聚焦一个可审查的任务；不要把未相关模块的修改混在一起。
- 进入 `main` 必须经 Pull Request；禁止直接推送 `main` 或强制推送共享分支。
- 至少一名其他成员进行人工审查；提交者负责处理意见和保持分支可集成。
- PR 至少说明：改了什么、为什么、影响哪些 API/数据/权限、如何验证、是否需要迁移或配置。
- API、状态、权限或数据库字段变化，先同步接口契约并通知受影响模块，再并行实现。
- AI 可协助实现和检查，但不计入另一名人类成员的审查。

## 8. 模块 Definition of Done

模块达到以下条件后才算完成：

- 页面主流程、加载/空/错误状态和窄屏布局均可使用。
- 前端通过真实 API 工作；Mock 仅用于开发，不作为最终验收依据。
- 服务端验证认证、角色、对象归属、状态转换和输入数据。
- 新增或变更数据库结构时包含 Flyway 迁移，并在本地目标数据库验证。
- 测试覆盖模块关键业务路径和高风险权限边界。
- `vue-tsc`/前端构建与 Maven 后端测试通过；跨模块流程通过冒烟测试。
- 文档、接口契约、OpenAPI 和演示步骤与实现保持一致。
- PR 经另一名成员审查并合并。

## 10. 建议的第一批任务

1. 共同任务：把当前后端路由、角色权限与 OpenAPI 导出作为接口基线，核对并修正文档差异。
2. 模块 A：完善游客公开列表与详情，验收未登录浏览和已发布内容过滤。
3. 模块 B：打通学生登录、提问、我的问题和登录后路由。
4. 模块 C：打通 HR 问题池、回答与运营审核队列，先使用团队演示账号。
5. 集成任务：贯通一条公开问答和一条私密工单，记录问题并分别归属模块负责人修复。

以上任务可并行开始，但任何跨模块契约必须先完成阶段 0 的确认。
