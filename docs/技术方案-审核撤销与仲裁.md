# 技术方案：审核撤销、审核次数限制与仲裁

> 版本：v1.0（方案稿，不含实现）
> 日期：2026-11-21
> 范围：问题、回答、追问三类内容；后台审核流；登录主体权限
> 命名：沿用 `moderation_*` 语系；新增权限表使用 `user_permissions`
> 依赖：本文以《技术方案-审核态与可见态解耦》v1.3 的 `moderation_status + visibility` 为基础，不改变其机审（L1/L2）设计

## 1. 结论摘要

1. **每个内容最多被人工审核 2 次**。每产生一次人工裁定（approve/reject）计 1 次；撤销不退还次数。
2. **裁定人可以在一定条件下撤销自己的裁定**：内容回到待审池（`L3 + HIDDEN`），但**撤销人不能再审同一内容**。
3. **撤销满 2 次的内容进入“待仲裁”**：仍然是 `moderation_status = 'L3'`，不新增审核态，由 `review_attempts >= 2` 派生；只有持有 `arbitrate` 权限的人能裁定。
4. **仲裁队列不单独建**，直接融合进普通审核池：待仲裁单子置顶、打角标、可单独筛选；**非仲裁员看不到待仲裁单子**。
5. **仲裁员也是普通审核员**，只是额外拥有 `arbitrate` 权限，不新增角色。仲裁员的任何 `approve/reject` 都按仲裁处理（终局），普通审核员是否走仲裁由“裁定发生时的 `review_attempts`”决定。`admin` 视为拥有全部额外权限，其裁定同样为仲裁裁定。
6. **仲裁裁定为终局**：写 `stage = 'ARBITRATE'` 的记录，**无论判通过还是驳回，都不可撤销、不可改判**，避免“裁完再撤、无限循环”。
7. 权限采用最小模型：保留 `users.role` 做基础权限（`operator` 即可审核），新增 `user_permissions(user_id, permission)` 只存额外授权。不做完整 RBAC。
8. **收紧现有漏洞**：当前 `decide` 允许从 `APPROVED/REJECTED` 直接改判（[AdminServiceImpl.java:51](file:///D:/code/myproject/CareerQ/backend/shared.all/product.shared/product.service.impl/src/main/java/com/careerq/service/impl/AdminServiceImpl.java#L51)），必须收回到“仅 `L3` 可审”，否则 2 次限制形同虚设。

## 3. 状态清单与状态机

### 3.1 状态清单（不新增审核态）

**审核态 `moderation_status`**：

| 状态 | 含义 | 是否持久 | 说明 |
|---|---|---|---|
| `L1` | 关键词/规则审核 | 瞬时 | 创建时同步执行，内容表几乎不停留 |
| `L2` | AI 初审 | 瞬时 | 当前由 `l2-auto-pass=true` 跳过调用 |
| `L3` | 待人工审核 | 是 | **唯一的人工池状态**；首次待审、撤销回池、待仲裁都在此 |
| `APPROVED` | 人工通过 | 是 | 可见态 `VISIBLE` 或 `REMOVED` |
| `REJECTED` | 人工驳回 | 是 | 可见态 `HIDDEN` |
| `WITHDRAWN` | 作者撤回 | 是 | 终态，非审核层级 |

> **不新增 `ARBITRATION` 审核态**。待仲裁是一个派生标记（`L3 + review_attempts >= 2`），与队列融合的分页、筛选、权限判断一起处理；多一个审核态会让所有查询、可见性、计数、迁移都要多分支，收益只是显示更直白。

**可见态 `visibility`**：`HIDDEN` / `VISIBLE` / `REMOVED`，与审核态正交。

**派生展示态 `DisplayStatus`**：

| displayStatus | 条件 | 后台文案 |
|---|---|---|
| `REVIEWING` | `L3` 且 `review_attempts < 2` | 待审核 |
| `ARBITRATING` | `L3` 且 `review_attempts >= 2` | **待仲裁（新增）** |
| `PUBLISHED` | `APPROVED + VISIBLE` | 已发布 |
| `REJECTED` | `REJECTED` | 未通过 |
| `REMOVED` | `visibility = REMOVED` | 已下架 |
| `WITHDRAWN` | `WITHDRAWN` | 已撤回 |

`DisplayStatus.of()` 增加 3 参重载 `of(moderationStatus, visibility, reviewAttempts)`；作者/公开侧继续用 2 参版本，`L3` 一律显示“审核中”，不向作者暴露“待仲裁”。

**新增字段（不是状态）**：

- 三张内容表：`review_attempts INT NOT NULL DEFAULT 0`；
- `moderation_records`：新增 `decision = 'undo'`、`stage = 'ARBITRATE'`；
- 权限表：`user_permissions`。

### 3.2 合法状态组合

| moderation_status | visibility | displayStatus | 含义 |
|---|---|---|---|
| `L1` / `L2` | `HIDDEN` / `VISIBLE` | `REVIEWING` | 机审中（瞬时） |
| `L3` | `HIDDEN` | `REVIEWING` / `ARBITRATING` | 机审未放行、撤销回池、待仲裁 |
| `L3` | `VISIBLE` | `REVIEWING` / `ARBITRATING` | 先发后审，仍在人工环节 |
| `APPROVED` | `VISIBLE` | `PUBLISHED` | 正常发布 |
| `APPROVED` | `REMOVED` | `REMOVED` | 发布后被下架 |
| `REJECTED` | `HIDDEN` | `REJECTED` | 未通过 |
| `WITHDRAWN` | `REMOVED` | `WITHDRAWN` | 作者撤回 |

### 3.3 状态转移表

| 当前 | 动作 | 权限要求 | 下一个审核态 | 可见态 | 副作用 |
|---|---|---|---|---|---|
| — | 创建 | 系统 | `L1` | `HIDDEN` | 写 L1 记录 |
| `L1` | 机审 block | 系统 | `REJECTED` | `HIDDEN` | 写 L1 reject 记录 |
| `L1` | 机审 pass | 系统 | `L2` | `VISIBLE` | 计数 +1 |
| `L1` | 机审 review | 系统 | `L2` | `HIDDEN` | 写 L1 记录 |

| `L2` | L2 不通过 | 系统 | `L3` | `HIDDEN` | 原可见则计数 -1 |
| **`L3`（attempts < 2）** | `approve` / `reject` | `operator`，且未审过该内容 | `APPROVED` / `REJECTED` | `VISIBLE` / `HIDDEN` | `review_attempts + 1`，写 `stage = 'human'` 记录 |

| `L1/L2/L3` | 作者撤回 | 作者 | `WITHDRAWN` | `REMOVED` | 离开待审池；原可见则计数 -1 |

### 3.4 关键规则

1. **人工裁定只能从 `L3` 发起**。`REVIEW_STATUSES` 从 `L3/APPROVED/REJECTED` 收窄为仅 `L3`（`remove/restore` 仍按可见态操作，不受此限）。
2. **一次裁定计一次审核**。撤销不退还次数，因此 `review_attempts` 只有 `+1`，从不回退。
3. **同一内容每个人最多审一次**：“已审过”指该 target 上存在本人 `stage in ('human','ARBITRATE')` 且 `decision in ('approve','reject')` 的记录。撤销不解除该限制。
4. **只有裁定人本人能撤销自己的裁定**。
5. **仲裁裁定不可撤销、不可改判**：凡是持有 `arbitrate` 权限的人做出的 `approve/reject`，无论当时 `review_attempts` 是多少，都写 `stage = 'ARBITRATE'` 并终局；一律禁止 undo，也禁止任何人对该内容再次裁定，否则会形成“仲裁员互相撤销”的死循环。
6. **`remove/restore` 不属于审核**：不消耗次数、不触发仲裁、不写 `human` 裁定的 from/to 语义（沿用现有记录方式）。
7. **撤销把内容变为 `HIDDEN`**：即使原来 `APPROVED + VISIBLE`，撤销后也不允许在待审期间继续可见。

## 4. 审核次数与撤销

### 4.1 `review_attempts` 语义

- 定义：该内容**历史上发生的人工裁定次数**（`approve` / `reject`），含仲裁裁定；不含 `undo`、`remove`、`restore`、机审。
- 存储：三张内容表各一列，与 `moderation_status` 同事务更新，使用条件更新防并发。
- 限制：`review_attempts` 到达 2 后，普通审核员不再具备裁定资格；只有仲裁权限可以继续处理。仲裁权限者的所有裁定（不论次数）都是终局。

### 4.2 撤销规则

撤销入口只出现在“我审核的”，且需同时满足：

1. 内容当前审核态为 `APPROVED` 或 `REJECTED`；
2. 该 target 最近一条人工裁定（`decision in ('approve','reject','arbitrate')`）的 `operator_id` 是当前用户；
3. 该裁定记录 `stage = 'human'`（`ARBITRATE` 不准撤销）。

撤销执行（事务内，先 `FOR UPDATE` 锁行）：

```sql
UPDATE answers
SET moderation_status = 'L3',
    visibility        = 'HIDDEN',
    moderation_reason = #{note},
    moderated_at      = current_timestamp,
    updated_at        = current_timestamp
WHERE id = #{id}
  AND moderation_status IN ('APPROVED', 'REJECTED');
```

影响 0 行返回 409。随后写一条 `moderation_records`：`stage='human'`、`decision='undo'`、`from_moderation_status=原状态`、`to_moderation_status='L3'`、`operator_id=当前用户`。若原可见态为 `VISIBLE`，在同一事务内扣减 `answer_count` / `followup_count`。

### 4.3 仲裁规则

- **触发**：普通审核员在 `L3` 且 `review_attempts >= 2` 时失去裁定资格，内容进入“待仲裁”；即“第一个人审了撤回、第二个人审了撤回”后，内容回到池中并自动成为待仲裁。
- **资格**：拥有 `arbitrate` 权限，且本人未审过该内容。`ADMIN` 角色视为拥有全部额外权限。
- **记录**：仲裁权限者的 `approve/reject` 无论当时 `review_attempts` 是多少，都写 `stage='ARBITRATE'`，与普通人工记录区分，供“已审”查询和终局判断使用。
- **终局**：仲裁裁定不论 `approve` 还是 `reject`，都不可撤销、不可被任何人改判；不提供申诉/再审入口。

## 5. 权限模型

### 5.1 表设计

```sql
CREATE TABLE user_permissions (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id    BIGINT      NOT NULL,
    permission VARCHAR(32) NOT NULL,
    created_at DATETIME    NOT NULL
);
CREATE UNIQUE INDEX uk_user_permissions ON user_permissions (user_id, permission);
```

- `permission` 本期唯一取值：`arbitrate`。
- `role` 不迁入此表：基础能力（能否进入后台、能否普通审核）仍由 `users.role = operator/admin` 决定；此表只存**额外**授权，与 `users.role` 是“或”的关系。
- 不建 `roles` / `role_permissions`：当前只有一种额外权限，完整 RBAC 属于过度设计。

## 6. 队列融合

### 6.1 查询与排序

待审池仍直接查三张内容表，不建仲裁队列表：

- 基础条件：`moderation_status = 'L3'`；
- **非仲裁员**：附加 `review_attempts < 2`，待仲裁单子直接不返回（避免点进去 403）；
- **仲裁员**：返回全部 `L3`；
- 排序：`arbitrationRequired desc` → `risk_level`（high → watch → normal → unrated）→ `created_at asc` → `id`。

现有实现是内存排序（[AdminServiceImpl.java:113](file:///D:/code/myproject/CareerQ/backend/shared.all/product.shared/product.service.impl/src/main/java/com/careerq/service/impl/AdminServiceImpl.java#L113)），本期沿用，只增加排序键；数据量增长后再改为 SQL 排序分页。

### 6.2 列表与筛选

`ReviewItem` 增加：

| 字段 | 类型 | 说明 |
|---|---|---|
| `reviewAttempts` | int | 已用审核次数 |
| `arbitrationRequired` | boolean | `attempts >= 2` |
| `canUndo` | boolean | 当前用户是否可撤销（本人最新裁定且非仲裁） |

队列筛选新增 `arbitration=true/false`（仅仲裁员可用）；前端在筛选栏显示“待仲裁”选项，表格行加“待仲裁”角标，并展示 `已审 1/2`。

### 6.3 “我审核的”与撤销入口

- 仍按 `operator_id` 查询最新人工记录，但需调整：

## 7. 数据库迁移 V12

文件：`V12__moderation_review_attempts.sql`

```sql
-- 1) 审核次数
ALTER TABLE questions ADD COLUMN review_attempts INT NOT NULL DEFAULT 0;
ALTER TABLE answers   ADD COLUMN review_attempts INT NOT NULL DEFAULT 0;
ALTER TABLE followups ADD COLUMN review_attempts INT NOT NULL DEFAULT 0;

-- 2) 回填：只统计人工裁定（approve/reject），兼容历史的 stage='L3'
UPDATE questions q SET review_attempts = (
    SELECT COUNT(*) FROM moderation_records r
    WHERE r.target_type = 'question' AND r.target_id = q.id
      AND r.stage IN ('human', 'L3') AND r.decision IN ('approve', 'reject')
);
UPDATE answers a SET review_attempts = (
    SELECT COUNT(*) FROM moderation_records r
    WHERE r.target_type = 'answer' AND r.target_id = a.id
      AND r.stage IN ('human', 'L3') AND r.decision IN ('approve', 'reject')
);
UPDATE followups f SET review_attempts = (
    SELECT COUNT(*) FROM moderation_records r
    WHERE r.target_type = 'followup' AND r.target_id = f.id
      AND r.stage IN ('human', 'L3') AND r.decision IN ('approve', 'reject')
);

-- 3) 归一化人工审核记录的 stage（V11 存量写成了 'L3'，代码实际写 'human'）
UPDATE moderation_records SET stage = 'human' WHERE stage = 'L3';

-- 4) 额外权限表
CREATE TABLE user_permissions (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id    BIGINT      NOT NULL,
    permission VARCHAR(32) NOT NULL,
    created_at DATETIME    NOT NULL
);
CREATE UNIQUE INDEX uk_user_permissions ON user_permissions (user_id, permission);
```

索引：待审查询沿用 `idx_questions_l3 / idx_answers_l3 / idx_followups_l3`；`review_attempts` 目前只在已加载的 `L3` 集合上过滤，暂不加索引。

演示数据固定三名运营（`13800000004` 已被 HR 王浩然占用，仲裁运营改用 `13800000007`）：

- `13800000003`（运营小助手）：无 `arbitrate` 权限；

两名普通运营可覆盖「A 审 A 撤 → B 审 B 撤 → 进入待仲裁」以及非仲裁员的队列隐藏；仲裁运营在任意审核次数下的裁定均为终局，可覆盖待仲裁裁定与“首审即终局”场景。

## 11. 并发与边界

| 场景 | 处理 |
|---|---|
| 两人同时裁定同一 `L3` | 行锁 + 条件更新；后提交者 409 |
| 裁定与撤销并发 | 撤销同样 `FOR UPDATE`；状态不符时 409 |
| 本人已审但记录查询与更新之间 | 在锁内校验记录归属，再条件更新 |
| 符合资格的人全部已审过 | 仲裁权限者做出的裁定均为终局、不可撤销，不会再产生“唯一仲裁员撤销后锁死”的新数据；历史 human 记录仍按原规则处理 |
| 内容被编辑后重审 | 本期不提供编辑重审；如后续支持，按“新一轮审核”重置 attempts 与审核人排除，另行设计 |
| 举报下架 | `remove` 只改可见态，不消耗次数、不改变审核结论 |
| 批量操作部分失败 | 当前语义为整体回滚，前端提示失败原因 |

## 13. 测试与验收

| 场景 | 预期 |
|---|---|
| A 审通过 | `APPROVED + VISIBLE`，`attempts = 1`，记录 `stage=human` |
| A 撤销 | 回到 `L3 + HIDDEN`，`attempts = 1`，记录 `decision=undo`；A 再次裁定被 403 |
| B 审核并撤销 | 回到 `L3`，`attempts = 2`，进入待仲裁，前端角标与置顶 |
| 普通运营裁定待仲裁内容 | 403；该内容对其不可见 |
| 仲裁员裁定 | `APPROVED/REJECTED`，记录 `stage=ARBITRATE`、`attempts=3` |
| 仲裁员撤销自己的仲裁裁定 | 403 |
| 任何人对已仲裁的内容发起裁定/撤销 | 403/409，结论保持不变 |
| A 撤销后查看“已审” | 列表不出现该内容 |
| 同一人重复审核 | 403 |
| 两人并发裁定 | 一个成功，另一个 409 |
| 撤销已发布内容的可见性 | 立即变 `HIDDEN`，回答/追问计数同步 -1 |
| 非仲裁员查询队列 | 不返回待仲裁内容 |
| 权限回收后旧会话 | 仍可仲裁，直至重新登录（已知限制，写入验收说明） |

回归范围：原有审核通过/拒绝、下架/恢复、举报处理、feed 可见性、HR 工作台计数、`AdminContextTests`。

## 14. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 收紧为“仅 L3 可裁定”改变现有行为 | 依赖直接改判的流程失效 | 明确改为“先撤销再处理”；同步更新测试与冒烟脚本 |
| 存量 `review_attempts` 回填偏差 | 待仲裁判定错误 | 迁移脚本只统计 approve/reject，并抽样对账；空记录默认 0 |
| 权限会话固化 | 授权/回收不立即生效 | 文档标注需重新登录；后续可改为每请求读取或会话刷新 |
| 资格人耗尽导致卡单 | 内容长期停在 L3 | 演示数据固定两名运营；极端情况由 `admin` 兜底，本期不提供人工转仲裁 |
| 仲裁裁定被误认为可申诉 | 用户/运营期待改判 | 文档与前端明确仲裁为终局，不提供撤销/申诉入口 |
| 仲裁死循环 | 两位仲裁员互相撤销 | 仲裁裁定禁止 undo（硬约束） |
| “已审”口径变化 | 用户找不到已撤销的单子 | 已审排除 undo，详情记录保留时间线；必要时后续增加“已撤销”筛选项 |
| 批量操作整体回滚 | 一条失败导致全部失败 | 沿用现状，前端展示失败原因；后续可改逐条结果 |

## 15. 已确认与待拍板

已确认：

1. 演示环境固定两名运营：一名有 `arbitrate` 权限、一名没有（见第 7 节）。
2. 仲裁裁定（无论通过还是驳回）终局，不可撤销、不可改判；`admin` 拥有最高权限（视为拥有全部额外权限），但本期不为其设计专门改判流程。

待拍板：

1. **已撤销单子的可见位置**：“我审核的”直接排除，还是保留一个“已撤销”筛选？建议先排除。
2. **权限变更生效方式**：接受重新登录，还是每次后台请求实时查 `user_permissions`？建议本期接受重新登录。
3. **内容编辑后的审核轮次**：本期不做；若后续支持编辑，需要定义 attempts 重置与审核人排除的轮次边界。
