## 0. 结论先行

新流程把产品从「**公开问答库**」改成「**先私密问答、再可选公开沉淀**」。
它与 v1 策划书写死的「**明确不做：私信**」「所有互动公开、异步、留痕、可审核」**直接冲突，二者不能同时成立**，必须先裁决再动代码与数据模型。

本文只做三件事：整理 v2 流程、列出冲突、给出可执行方案与待确认项。**不修改**已确认的策划书与技术方案。

## 1. 用户流程 v2（按用户原文整理）

**阶段一：提问（私密）**

1. 完善信息（可选）：年级、学历、实习目标等，用于更精准匹配。
2. 提交问题：问题进入**私密问题池**（Q1…Qn），此时仅自己可见（或仅被指定 HR 可见）。

**阶段二：HR 解答与互动（闭环）**

3. HR 认领/解答问题池中的问题。
4. 追问与复核：用户觉得「不够清晰」可在原帖内追问，HR 继续解答，直到用户认为「可以了」。
5. 关闭问题：用户确认解答完毕，状态标记「关闭」并归档。

**阶段三：知识沉淀（公开）**

6. 决定公开：归档时或之后，用户可把高质量问答「投入公共池」。
7. 公共浏览：新用户先浏览公共问题池，建立对平台的信任。
8. 公共追问：新用户可直接在公开问题下追问，引入新人或 HR 参与。

**技术流程要点（用户原文）**

- 身份与鉴权：Users 表存 Profile，按角色分权限（HR 拥有回答权限）。
- 核心表：`Private_Questions`、`Public_Posts`、`Followups`。
- 状态流转：提问入私密表；回答/追问更新 Followups 与状态；**关闭时用事务**把私密记录复制/转换为公共记录。
- 前端：私密工作区（Q1—Qn 与对话流）+ 公共广场（搜索、按学历/年级筛选、二次追问）。

## 2. 与 v1 的冲突清单

| 维度 | v1 策划书（已落档） | v2 新流程 | 冲突性质 |
|---|---|---|---|
| 产品定位 | 公开、异步、结构化职业问答**信息库** | 私密问答工单 + 可选公开沉淀 | **定位级**，不是细节差异 |
| 明确不做 | 私信、好友、实时聊天 | 私密问题池、私密追问线程 | **直接冲突**（虽非实时 IM，但内容不公开） |
| 可见性 | 所有互动公开、留痕、可审核 | 默认仅提问者与 HR 可见 | **合规模型改变** |
| 审核范围 | 公开内容机审 + 人审 | 私密内容同样承载违法/歧视/招聘诈骗风险 | 审核责任**不因私密而消失**，风险反而更高 |
| 冷启动指标 | 「公开问题 48 小时内至少 1 个有效回答」 | 「私密问题被认领并解答」 | 指标口径需重定义 |
| 数据模型 | questions / answers / followups | private_questions / public_posts / followups | 表结构需重构 |
| 前端形态 | 公共广场为主 | 私密工作区为主 + 公共广场 | 页面结构需重排 |
| 对外表述 | 「不做社交、不做私聊」 | 私密问答本质上是 1 对 1 咨询 | 宣传口径需改，否则**涉嫌虚假宣传** |

> 关键判断：v2 的「私密」不是实时聊天，而是**异步问答工单**。技术上可以做到「不是 IM、不留外部联系方式」，但它仍然改变了「所有互动公开」这条合规基石。不能只改前端、不改审核与法务表述。

## 3. 三种裁决方案

### 方案 A：v2 取代 v1（私密优先）

- 定位改为「私密职业问答工单 + 优质内容公开沉淀」。
- 优点：贴近真实需求——简历、求职困惑、薪资期望等**学生本来就不愿公开发**；私密提高提问意愿，公开沉淀保留内容资产。
- 代价：合规与审核成本最高；需重写策划书定位、不做清单、冷启动指标与宣传口径。

### 方案 B：维持 v1（公开优先），v2 仅作未来功能

- 优点：与已投稿材料一致，合规风险最低，MVP 范围不变。
- 代价：真实痛点覆盖不足，冷启动可能「没人敢公开问」。

### 方案 C：混合（**推荐**）

- 提问时二选一：**公开提问** 或 **私密工单**。
- 私密问答与公开内容**走同一套审核**（机审 + 人审 + 举报），只是可见范围不同。
- 关闭后由用户主动选择「脱敏公开」，公开前**二次审核 + 身份脱敏**。
- 保留「不做实时 IM」边界：私密是异步工单，不是聊天；不提供好友、在线状态、即时消息。
- 优点：兼顾提问意愿与内容沉淀，改动集中在数据模型与审核策略，不推翻全部定位。
- 代价：MVP 工作量增加约 30%——多一张私密问题表、一套线程、一套公开转换流程。

## 4. 若采纳 v2 / 方案 C：必须补的控制点

| 风险 | 必修控制 |
|---|---|
| 私密通道传播违法内容 | 私密内容**同样 100% 机审**，高风险转人审；不因「私密」跳过审核 |
| 私下交易、招聘诈骗 | 拦截联系方式（手机号/微信/QQ）、招聘承诺、索要简历；HR 侧同样限流与风控 |
| 隐私泄露 | 私密内容仅 author + assigned HR + 运营（审核）可见；运营访问留痕 |
| 公开时泄露身份 | 公开前默认脱敏：隐去真实姓名、企业全称、学校、时间；用户可预览确认 |
| 未成年人 | 未满 18 岁限制私密问答范围，提示监护人/学校合规要求 |
| 内容归属与删除 | 明确公开内容的授权与撤回机制；关闭/删除时软删 + 下架 |
| 被误认为官方 | 首页固定声明「个人项目，非学校官方」，私密问答同样展示 |

## 5. 若采纳，技术方案需要的改动（相对 v0.2 Web 版）

### 5.1 数据模型

```text
private_questions
  id, author_id, title, body, status(open/answered/followup/closed),
  assigned_hr_id(nullable), is_public(bool), public_post_id(nullable),
  closed_at, created_at, updated_at

private_followups        -- 私密线程（不是 IM，是结构化追问列表）
  id, private_question_id, sender_id, sender_role(user/hr), body, created_at

public_posts
  id, original_question_id, title, question_body, hr_answer,
  anonymized(bool), published_at, status(pending/published/reviewing/removed)

-- 现有 questions / answers 继续服务「公开提问」路径；或统一为 content + scope(public/private)
```

推荐：**统一内容表 + `scope` 字段**（`public` / `private`），避免两套逻辑复制；`followups` 通过 `scope` 区分公开追问与私密线程。

### 5.2 状态机

```text
私密问题：open → assigned → answered → followup → closed → public_archived(可选)
公开帖子：pending → published → reviewing(被举报) → published / removed
```

- 关闭 → 公开必须是**用户主动动作**，且经过二次审核与脱敏，不能自动同步。
- 公开后原私密记录保留只读映射，支持撤回。

### 5.3 API 变化

```text
POST /private-questions                       # 私密提问
GET  /private-questions/mine                  # 我的问题（Q1..Qn 工作区）
GET  /hr/private-question-pool                # HR 可认领池（不含匿名外泄）
POST /private-questions/{id}/answers          # HR 认领并回答
POST /private-questions/{id}/followups        # 追问
POST /private-questions/{id}/close            # 关闭归档
POST /private-questions/{id}/publish          # 申请公开（二次审核 + 脱敏）
GET  /public-posts                            # 公共广场
POST /public-posts/{id}/followups             # 公共追问
```

### 5.4 审核

- 私密与公开共用审核状态机，但**风险分级不同**：私密内容 P1 起就要人审。
- 公开转换时做「脱敏检查 + 二次审核」，两项都通过才发布。
- 所有运营查看私密内容的行为写审计日志。

## 6. 「Qoder Sites」的影响（关键待确认）

用户技术流程提到「结合 **Qoder Sites 的全栈能力**」。这可能是比赛指定的开发/托管平台，影响远大于流程本身：

| 问题 | 为什么关键 |
|---|---|
| Qoder Sites 是否**强制**使用？ | 强制则现技术方案 v0.2（FastAPI + PostgreSQL + Redis + Caddy）需整体重写为平台内建能力 |
| 平台是否提供**内建数据库**？类型与容量？ | 决定 Private_Questions/Public_Posts 能否直接落地，是否需要外部 DB |
| 是否支持**自定义后端/后端函数**？ | 决定审核异步任务、大模型调用、短信验证码能否实现 |
| 是否支持**第三方 API 调用**？ | 内容安全、短信、对象存储都依赖外部服务 |
| 部署、域名、HTTPS、访问控制 | 决定能否交付「真实可访问 Demo」 |

**结论**：在确认「是否强制 Qoder Sites」之前，不建议按 v2 重写技术方案——否则可能白做。当前 v0.2 仍可作为「自建方案」备选。

## 7. 对指标与冷启动的影响

- 冷启动核心指标从「公开问题回应率」改为：
  - **私密问题认领率**（发出后 48h 内被 HR 认领）；
  - **私密问题解决率**（被用户标记「已解决/关闭」）；
  - **公开沉淀率**（关闭问题中选择公开的比例）——这是内容资产的真正来源。
- 冷启动顺序建议：先用私密问答跑通「有回应」，再用公开沉淀建立信任；与 v1 的「先公开」相反。
